# Условное принятие групповых команд

Выбрана общая сохранённая ревизия принятия команд одного диалога. Изменение
состава, сообщение и ACK условно фиксируются вместе с результатом команды;
конфликт требует загрузить свежий состав и заново проверить доменные правила.
Это связывает успешную запись с тем составом, по которому проверены права.
Одна доменная версия без атомарной проверки хранилищем не закрывает гонку.

Сериализация через единственного владельца очереди тоже допустима, но требует
отдельного протокола владения при restart/rebalance. В этой application-итерации
принимается контракт условных записей; каждый конкретный handler координирует
свой сценарий, а атомарность обеспечивает реализация репозитория.

Для Cassandra требование — conditional batch в одной таблице и partition:
строка ревизии, результат команды и durable подтверждение должны принадлежать
одной границе. [Cassandra CQL: BATCH и conditional updates](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/dml.html)
и [ограничение conditional batch на одну таблицу](https://issues.apache.org/jira/browse/CASSANDRA-10085).
CAS строки состава, за которым следует обычный INSERT в другой partition,
не удовлетворяет выбранному контракту.

No-op ACK и replay сообщения проходят ту же проверку ревизии, сохраняя
доменные версии и время. Timeout с неустановленным исходом не считается
отказом CAS; адаптер разрешает его по сохранённому подтверждению команды
или сообщает недоступность без успешного ответа.

Отдельные чтения сообщений, send key, receipts и результатов команд состава
привязываются к `GroupSnapshot.revision` через обязательный `at_revision`.
Если состояние этой ревизии не подтверждено, включая отсутствие записи,
адаптер поднимает `GroupReadConflictError`; handler заново загружает группу.
Устаревший `None` не означает отсутствие принятой отправки или watermark.

Условная запись также атомарно запрещает дубль send key/Message ID и откат
READ/DELIVERED. Позиция новой отправки следует за `last_position`, receipt
сохраняет идентичность и следующую версию. Одной проверки общей revision
недостаточно, если независимое чтение ранее дало устаревшие данные.

Команды состава принимают стабильный `command_id` от вызывающего кода.
`try_commit_membership` использует ту же общую атомарную границу, сохраняет
намерение и результат вместе с составом. Повтор `(dialog_id, command_id)`
читает результат; другое действие, actor или целевой user дают конфликт.
Восстановление результата не применяет прежнее изменение поверх более нового
состава. Клиент сохраняет ID при retry и назначает новый для нового действия.

Для отправок используется текущая редакция Message и неизменяемый send key.
До первого реального редактирования содержимое обязано совпадать; после него
различия текста игнорируются. Исходное содержимое и fingerprint для проверки
replay не сохраняются. Полный контракт описан в
[доменном проекте](../domain-model-design-2026-09-18.md#идемпотентность-отправки).

Схема Cassandra и адаптер здесь не создаются. При реализации надо определить
bounded retention журнала принятия и перенос в history/sync projections,
сохраняя возможность восстановить незавершённые эффекты. Нужны реальные
конкурентные проверки нескольких writers, неизвестного исхода LWT и crash
между фиксацией результата и последующими проекциями.
