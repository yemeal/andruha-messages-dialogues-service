# Редактирование текста сообщения

`Message` наследует `VersionedMutableEntity`. Автор редактирует текст через
`edit_text`; вложения, идентичность отправки, позиция и время создания сохраняются.
Это доменный этап: API, долговременное сохранение, события и frontend ещё не подключены.

## Поведение

```python
changed = message.edit_text(
    actor_id=author_id,
    text="Исправленный текст",
    now=edit_time,
)
```

Проверка автора выполняется первой, включая повторы без изменений.
Проверка текста переиспользует `MessageContent` и `MessageText`: нормализацию
Unicode NFC, переводов строк и пробелов по краям, а также лимит 4096 символов.
`None` и пробельная строка снимают подпись у сообщения с вложениями.
Оставить сообщение без текста и вложений нельзя.

Новый неизменяемый `MessageContent` передаётся в существующий `_apply_changes`.
Полное кандидатное состояние проверяется до замены текущего. Ошибки автора,
содержимого или времени не меняют текст, версию и метаданные редактирования.

| Сценарий | Версия | Время правки | `is_edited` |
|---|---|---|---|
| Новое сообщение | 1 | `None` | `False` |
| Повтор того же нормализованного текста | 1 | `None` | `False` |
| Первая реальная правка | 2 | Время правки | `True` |
| Повтор последней правки | 2 | Прежнее время | `True` |
| Ещё одна правка, в том числе возврат к первоначальному тексту | 3 | Новое время | `True` |

Время имеет часовой пояс и нормализуется в UTC. Оно не предшествует созданию
или предыдущей правке. Равное время допустимо: две правки могут попасть в один
тик часов. Поэтому признак редактирования нельзя вычислять сравнением
`updated_at > created_at`.

## Данные для frontend

Домен предоставляет два семантических свойства:

- `message.is_edited`: было ли хотя бы одно реальное редактирование;
- `message.edited_at`: время последнего редактирования или `None`.

Они читают `updated_at`. Это обычные свойства, которые не добавляются автоматически
в `model_dump` и не дублируют хранимое состояние. Будущий application DTO явно
отображает их в `isEdited` и `editedAt`; версия передаётся как `messageVersion`.

Пример метаданных нового сообщения:

```json
{
  "messageVersion": 1,
  "isEdited": false,
  "editedAt": null
}
```

Пример после реальной правки:

```json
{
  "messageVersion": 2,
  "isEdited": true,
  "editedAt": "2026-09-30T10:30:00Z"
}
```

Frontend показывает отметку по `isEdited`, время — по `editedAt`, а версию
использует для защиты от устаревших обновлений одного сообщения.
Это предложение следующего транспортного контракта, а не действующая схема
`message.v1`. Она запрещает дополнительные поля и меняется отдельно вместе
с потребителями.

В текущем домене версия растёт только при изменении текста, поэтому
`version > 1` эквивалентно `is_edited`. Это условный контракт, а не универсальное
значение версии для OCC. Если появятся удаление, модерация или другие мутации
сообщения, потребуется отдельная хранимая метка редактирования текста.
Явные поля frontend позволяют изменить внутренний источник без смены смысла API.

## Восстановление

Снимок содержит `version` и `updated_at`. Версия 1 с временем правки и версия
выше 1 без времени правки отклоняются с `InvalidMessageEditMetadataError`.
`model_validate` и `model_validate_json` сохраняют версию и время; восстановление
само не считается редактированием. Старый снимок без обоих новых полей
восстанавливается с версией 1 и без отметки правки.

## Следующее подключение

Application должен получать автора из доверенного principal, загружать сообщение
и соответствующий диалог, проверять текущий доступ, вызывать `edit_text` и сохранять
результат с ожидаемой версией. Версия в Python-объекте не заменяет условную запись
в репозитории. Доступ к группе и изменение её состава требуют согласованного
протокола сохранения; одной проверки загруженного состава недостаточно для гонок.

Повтор команды редактирования должен восстанавливать её прежний результат
и публикацию, сохраняя более поздние правки. Один доменный `False` не доказывает,
что события и проекции предыдущей операции уже завершены.

Для проверки повторной отправки хранится только текущая редакция сообщения
и его неизменяемый ключ. До первой правки сравнивается нормализованное
содержимое. После реальной правки текст повтора не сравнивается: отправка «А»
после правки в «Б», как и любой другой допустимый текст с тем же ключом,
возвращает актуальную редакцию «Б». Диалог, автор и упорядоченные вложения
по-прежнему должны совпадать. Отдельный исходный текст и fingerprint не нужны.
Это сознательный компромисс: переиспользование ключа для нового текста после
правки не даёт конфликт, но и не создаёт новое сообщение. Новая отправка
обязана получить новый `client_message_id`; прежний ID — ошибка клиента.
Бэкенд возвращает существующее сообщение и не перезаписывает его текст,
не обещая выявлять новое намерение клиента после редактирования.
Достройка истории из старого снимка не перезаписывает более новую версию.

После сохранения нужен надёжный путь доставки правки получателям и в sync.
Позиция сообщения остаётся прежней, поэтому курсор только по позиции новых
сообщений не обнаружит редактирование старого. ReceiptWatermark продолжает
подтверждать сообщение по его позиции; правка не сбрасывает доставку и прочтение.

## Проверяемые границы

Тесты используют `Message.create`, `edit_text`, свойства, сериализацию и
восстановление. Они проверяют нормализованные повторы до и после первой правки,
права автора, неизменность отправки и вложений, снятие подписи, ошибки времени
и текста, возврат к старому тексту, одинаковое время нескольких правок,
совместимость старых снимков и согласованность метаданных.

Доменный набор не доказывает работу Cassandra, Kafka, API или frontend.
