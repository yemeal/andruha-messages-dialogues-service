# Доменный слой Messages and Dialogues Service

Доменный слой представляет собой изолированное ядро сервиса, реализованное по принципам **Domain-Driven Design (DDD)** и
**Hexagonal Architecture (Ports and Adapters)**.

Слой не зависит от внешних фреймворков (FastAPI), базы данных (Cassandra), брокеров сообщений (Kafka) или других
внутренних слоёв сервиса (`application`, `infrastructure`, `entrypoints`).

---

## 1. Базовые абстракции (`app.domain.base`)

* **`DomainModel`** — корневая модель предметной области на базе Pydantic v2.
    * Все модели по умолчанию **заморожены** (`frozen=True`) для защиты инвариантов от прямых присваиваний снаружи.
    * Запрещены неизвестные поля (`extra="forbid"`).
    * Настроена строгая валидация дефолтов (`validate_default=True`) и запрет произвольных типов (
      `arbitrary_types_allowed=False`).
    * Пробелы и переносы строк в строковых данных не обрезаются (`str_strip_whitespace=False`).
* **`Entity`** — неизменяемая базовая сущность. Содержит уникальный идентификатор `id: UUID` (для новых записей
  генерируется серверный UUIDv7) и метку времени создания `created_at: datetime` (строго в UTC).
* **`MutableEntity`** — базовый класс для изменяемых сущностей. Содержит метку времени последнего обновления
  `updated_at: datetime | None` и протокол безопасных атомарных мутаций.
* **`VersionedMutableEntity`** — изменяемая сущность с поддержкой оптимистических блокировок (**Optimistic Concurrency
  Control, OCC**). Содержит целочисленную версию `version: int >= 1`, которая монотонно увеличивается на 1 при каждом
  реальном изменении состояния.

---

## 2. Протокол изменения состояния сущностей

Все сущности и Value Objects спроектированы как **Rich Domain Models**: они сами управляют своим состоянием и
инвариантами, скрывая техническую логику валидации.

### ВАЖНО: Как правильно изменять состояние сущности

1. **Прямое присваивание полей запрещено**:
   ```python
   # ОШИБКА: вызовет ValidationError (frozen_instance)
   watermark.read_through = new_checkpoint
   ```
2. **Изменение происходит ТОЛЬКО через публичные бизнес-методы**:
   Каждая мутация должна отражать действие на языке предметной области (Ubiquitous Language):
   ```python
   # ПРАВИЛЬНО: явный бизнес-метод агрегата
   chat_settings.rename(new_title="Команда проекта", now=now)
    ```
3. **Внутри бизнес-метода вызывается защищённый `_apply_changes`**:
   ```python
   class ChatSettings(VersionedMutableEntity):
       title: Annotated[str, Field(min_length=1, max_length=100)]
       is_muted: bool = False

       def rename(self, new_title: str, now: datetime) -> bool:
           # 1. Если new_title == self.title: _apply_changes сам вернёт False (no-op без ручных if).
           # 2. Если new_title невалиден: упадёт ValidationError, а состояние останется прежним.
           # 3. Если изменился и валиден: обновит title, version + 1, updated_at и вернёт True.
           return self._apply_changes(now=now, title=new_title)

       def mute(self, now: datetime) -> bool:
           # Повторный вызов mute() автоматически вернёт False без изменения версии
           return self._apply_changes(now=now, is_muted=True)
   ```

### Что гарантирует `_apply_changes(*, now, **changes)`

Метод `_apply_changes` инкапсулирует 4 обязательных шага:

1. **Изолированная валидация кандидата**: создаётся отдельный временный объект с новыми значениями. Все
   Pydantic-валидаторы и инварианты модели проверяются на нём. Исходный объект `self` не затрагивается.
2. **Детекция No-Op (идемпотентность)**: если новые значения совпадают с текущим состоянием (`candidate == self`), метод
   сразу возвращает `False`. Версия и время не увеличиваются, лишние события в Kafka не генерируются.
3. **Валидация времени и рост версии**: на кандидате вызывается `_mark_updated(now)`. Проверяется, что `now` имеет
   таймзону и не откатывает время назад (`now >= updated_at` и `now >= created_at`). Для `VersionedMutableEntity` версия
   кандидата увеличивается на `+1`.
4. **Атомарная фиксация**: проверенное состояние кандидата подменяется в `self` через `_replace_state`. Метод возвращает
   `True`.

> **Гарантия целостности**: если валидация или проверка времени падает с ошибкой, исключение прерывает выполнение, а
> сущность гарантированно остаётся в исходном валидном состоянии (никаких частичных мутаций).

### Особенности версионирования в `VersionedMutableEntity` (OCC)

* **Автоматический инкремент версии**: Разработчику агрегата не нужно вручную увеличивать `version` — наследуемый метод
  `_apply_changes` полиморфно вызывает `_mark_updated`, который атомарно увеличивает `version` ровно на 1 вместе с
  обновлением `updated_at`.
* **Защита от ложных конфликтов (No-Op)**: Если входящие аргументы эквивалентны текущему состоянию объекта,
  `_apply_changes` возвращает `False`, а версия и время остаются нетронутыми. Это исключает ложные конфликты OCC при
  идемпотентных повторах запросов или запоздалых доставках/прочтениях.
* **Разделение ответственности**: Доменная сущность гарантирует строгую монотонность версии и валидность состояния в
  памяти; репозиторий в слое адаптеров использует `version` для условной записи в хранилище (Cassandra LWT
  `IF version = :expected_version`).
